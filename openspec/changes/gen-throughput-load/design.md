## Decisions

1. **The cause is the CPU, not our caches.** Per-tile load time rises from 12.5 ms (1 worker) to 27.7 ms (18) while the part spent in blocks stays 0.15 to 1.8 ms; a fixed ALU kernel shows the same factors (1.4-1.6 at 8 threads, 2.2-2.6 at 18) and the standalone bench scales x8.1 on 20 threads. Window 3's further 1.8x did not reproduce. No code fix is warranted by this evidence; the counters are the deliverable so that window 4 can tell.
2. **Recorded only.** Counters are relaxed atomics on paths that already take a lock or decode a 16 MB block, or thread-local cells; the hot path of a read inside a pinned block is untouched (a shared atomic there would be the contention being looked for). The job log is a mutex-protected vector pushed once per job. Wall-clock readings never enter a decision, so requests, order and results are unchanged (CON-14); the existing dispatch-order and bit-identity tests run unchanged.
3. **Job time measured by the worker.** `JobLog::timed` wraps the source's load inside the job closure: the queue wait is dispatch to start, the concurrency is the number of loads inside their source when this one started. A job cancelled before it starts is not logged.
4. **A calibration beside the tiles.** `calibrate_cpu(threads)` runs a fixed ALU kernel once alone and once on `threads` threads at once and reports the single time and the median and maximum of the parallel times, before and after the case when nothing of the case runs. It reads the machine's state outside the code under test; the ratio is what threads cost each other.
5. **`load_` is a prefix, not a list.** The comparison skips every count with the prefix `load_`, so new counters need no change there.
