## Decisions

1. **Lower the workers, not raise the frame thread.** The ablation separates nothing between "workers below normal", "frame thread above normal" and both. Lowering is allowed to any process on both platforms; a raise needs privilege on Linux (nice -5). Only the workers are changed.
2. **Priority is set by the worker thread on itself, before its first job**, inside `ThreadPool::with_priority`. No handle passing, no OS call from the caller, and the calling thread is untouched (tested). `ThreadPool::new` stays at normal (the plan worker, tests and examples).
3. **The smallest platform abstraction: one module, two calls.** `priority::set_current` / `current`. Windows: `SetThreadPriority(GetCurrentThread(), THREAD_PRIORITY_BELOW_NORMAL)` (`windows` 0.62.2, feature `Win32_System_Threading`, already in the lock file through gpu-allocator). Linux: `setpriority(PRIO_PROCESS, gettid, 5)` (nice values are per thread on Linux; `libc`, already locked). Other platforms: reports not applied. Each `unsafe` block is one call with a stated invariant; a safe wrapper crate (`thread-priority`) would add a dependency and cannot express a Linux nice value.
4. **A refusal is not an error.** The call returns whether it applied; the pool works either way. The job results do not depend on it (CON-14): size, limit and request order are those of `GenWorkers`.
5. **Default below normal, `--gen-priority normal` restores the old behaviour.** The ablation shows no cost (medians, lag, dispatch per frame unchanged) and a smaller tail. `protocol.gen.priority` records it; a log without it is read as normal, so window 4's comparison against window 3 is named as different pools, not as a regression.
6. **Not a fix of window 3.** The window's slower generation did not reproduce on a quiet box; the change is the cheap, measured-no-cost half of the answer and window 4 decides whether more is needed.
