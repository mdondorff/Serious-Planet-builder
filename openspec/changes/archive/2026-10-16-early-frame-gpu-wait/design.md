## Decisions

- Cause. Window 2 shows a GPU wait of about 41 ms at dive frame 2 with sub-millisecond CPU columns, so the cost is GPU-side first use. On the RTX at 2560 x 1440 (ad hoc probe, compact, indirect, 553 nodes) a cold renderer's first waited frame took 3.1-3.8 ms against 0.7-0.9 ms later, and the F4 warm-up left 2.9-3.0 ms in frame 0; with this change 2.9-3.0 ms still remains in frame 0 in that probe, which is dominated by the 553 tiles' upload data that travels with the first submission. So the 41 ms of the dive is not reproduced by a probe on one plan, and window 3 decides whether the parts now warmed were the cause. Everything the measured frames use the first time, and that a throwaway frame can use too, is now used by it.
- What a throwaway frame can still not reach: pool blocks / atlases beyond the first (a scene's later placement), and the data of the first uploads. The first stays on demand (the share is a ceiling, STRM-006); the second is real work.
- Count-based guarantee: `FirstUse` records, per renderer, the distinct ring sets, pipelines, timestamp passes and draw modes any submission has used (masks updated by the warm-up and by every real frame) plus the warm-up's waited submissions. After `warm_up`, the numbers equal the maximum a scene's frames reach (ring sets = `RING_SETS`, pipelines of the format, the timed pass where the adapter supports it, the active draw mode); frames 0..3, untimed and timed, leave them unchanged; a cold renderer reaches `RING_SETS` only by its first two frames. No wall-clock assertion (CON-17, CON-20).
- The timed pass in the warm-up uses the renderer's own query set, resolve and readback buffers, mapping the readback once, as `render(.., true)` does. The pipelined loop does not time its frames, but the perf scenes' GPU column and the tests do.
- Two indirect records so the warm-up multi-draw has a count above one, which the frames' runs have; the records are degenerate (zeroed vertex data), no image changes (`warming_up_does_not_change_the_image` still holds).
- A ring grown by a larger plan builds a new set of buffers whose first use cannot be warmed; its mask resets and `ring_builds` counts it (REND-017 names plans within the warm ring, 2048 nodes).
- Call `set_draw_mode` before `warm_up`: the other mode is not warmed (FirstUse.draw_modes then reads 2 after a frame in it). A plan beyond the warm ring (2048 nodes) rebuilds the ring and resets its mask; that growth is counted by ring_builds.
