## Decisions

1. **The cause is the ranking, not the writes.** `upload_ms` covers the loop's whole upload half. The ablation (docs/learnings.md, "Upload time varies with the wants and the load") puts the slow frames' time in `Classes::of`, rebuilt every frame the draw wants change (the dive moves the camera every frame), and the tail in the contention of that 1 ms step with 16-20 busy threads. The renderer's staging and queue calls are 0.03-0.3 ms and do not move with the number of busy threads in the micro-benchmark.
2. **Same order, cheaper sets.** The draw class keeps its definition (every draw tile with all ancestors, a tile with the lowest priority at or below it). The walk stops at an ancestor already holding a priority at most its own, which is exact because every walk lowers all ancestors; the map is kept between builds. R's class is `ResidencySet::contains` (R is closed under parents, so its closure is the set), no set is built. The prefetch closure keeps its definition and is rebuilt only when the prefetch wants change. The upload order, and with it every digest, is unchanged (a unit test compares the early-stopping build with the definition over ascending, shuffled and tied priorities; the existing class-order tests run unchanged).
3. **Kept buffers, counted by capacity.** `BatchScratch` holds the staging of a batch. A test watches `batch_scratch_capacity` (the heap is not countable through wgpu). The waiting list, the batch and the draw wants vector of the loop are kept the same way.
4. **A reserve of two cores by default.** `GenWorkers::machine()` is `workers_for(cores, GEN_RESERVE)` = cores - 2, at least 1, at most cores (18 on the reference machine); `--gen-reserve N` changes it, `--gen-workers N` still fixes it. The request order is a function of the job limit, so the pool size changes timing, not results (CON-14); pinned digests state their own limit. The planner accepted a reserve of one or two cores. Two because the frame thread, the plan worker and the driver's threads are three consumers; it is a named default, not a measured optimum.
5. **Gen settings are facts of the log.** `protocol.gen` is `{workers, ahead, reserve|null}`. Reading is lenient (absent or null is none). Two logs that both have it and differ are not compared (the same rule as field and source); one without it is compared and the line names the pools; `accept` never reads it.
6. **No thread priorities.** Lowering the generation threads' priority needs unsafe FFI or a new direct dependency; the project avoids both. If window 3 shows a tail with the reserve, that is an ADR question.
