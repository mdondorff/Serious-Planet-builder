## Decisions

- **Slot = one vertex-format tile.** `(cells + 1)^2` grid vertices plus `4 (cells + 1)` skirt vertices at 44 B: 1,221 x 44 = 53,724 B at cells 32. ADR 0033's slot counts (230,640 mid, 353,648 high) are for the compact tile (8.8 KB); the share is a byte ceiling, so the vertex format gets fewer slots: **37,376 at the mid share (146 blocks of 256) and 57,344 at the high share (224 blocks)**, each of which holds the worst standard view's R (14,325 tiles, finest level 26) 2.6 and 4.0 times. The compact change replaces the main pool's slot and block, nothing else of this change.
- **The share is a ceiling counted in slots.** `PoolConfig::allocated_bytes()` = main blocks x block bytes + the small vertex pool (512 slots, 27.5 MB) + index buffer + node records (32,768 x 512 B, 16 MiB). `fit_share` takes the share minus the 0.125 GiB reserve, in whole blocks, and refuses a configuration whose fixed items do not fit the reserve (a big slot first halves the vertex pool, down to 128 slots, then gives it up). Blocks and the vertex pool are allocated on first use, lowest slot first, so a small scene touches few blocks; the model for what is live is `allocated_bytes_with(blocks, vertex_pool_live)`.
- **Pool = blocks of 256 slots.** A block is one `VERTEX | COPY_DST` buffer of at most 64 MiB (14 MB at cells 32), well inside wgpu's default 256 MiB. The draw binds `block.slice(slot offset, slot bytes)`: the same vertex data, the same indices, base vertex 0, so the image cannot change. Atlases and indirect multi-draw need the compact format and come later (ADR 0033 point 3's open points stay open).
- **Free list with retirement.** Lowest free index first (deterministic, compact). `release(slot, frame)` puts the slot in a retiring queue until `frame + retire_frames`; only then is it reusable. `retire_frames` is the frames in flight: the streamer defaults to 0 (a renderer that finishes a frame before the next begins), the renderer's own pools use 1, tier presets are meant for 2.
- **Reservation at dispatch.** A job reserves its slot when it is dispatched and gives it back when the job ends without a resident tile. Resident plus in-flight therefore never exceed the capacity, even between frames; the old soft "plus results arriving between frames" is gone (STRM-007 reworded). A request with no free slot blocks its pool for that frame; the pools are independent (levels 0-2 in the vertex pool never wait for the main pool).
- **Eviction is demand-driven and ordered.** Before dispatch the streamer counts the slots the next requests need (the first `max_in_flight x (1 + retire_frames)` queue entries, so the retirement delay does not stall the pool), subtracts the free and retiring slots, and evicts: tier 0 = tiles in no class or prefetch only (least recently used first); tier 1, for draw requests only = R-only tiles, farthest first and finest first. D with its ancestors and the roots are never victims. Residency requests never evict R tiles (no thrash for a want set the manager has not fitted); prefetch only takes free slots. A tile that left R stays until the share needs the space (hysteresis).
- **Degradation is a pure function** `degrade(D, R, capacity, vertex_split)`. The set is R plus D with ancestors plus the six roots. If it exceeds the capacity: (1) sibling groups whose members are all unpinned leaves are replaced by their parent, farthest first (the group's nearest member decides), then finest, then tile id, until it fits; (2) leftover unpinned leaves in groups that contain a pinned tile go one by one by the same order; (3) only if D with its ancestors alone still exceed the capacity (a budget failure, `budget_failure` in the report with the numbers) the same order runs with only the roots pinned and the D tiles it removes are asked for as their ancestors (`draw_replaced`: the declared LOD-008 exception). The merge sequence does not depend on the capacity, so the results are nested (a smaller share only removes more) and a pure function of the sets.
- **Levels 0-2 do not count against the capacity** when the small vertex pool exists (at most 126 tiles of the 512 slots; the pool also takes the CON-13 fallback tiles of ADR 0033 point 5 when the compact format exists) and are never merged away.
- **Headroom pins are counts**, measured at the ten standard views over the default world (256-cell bake, cells 32, tau 6 px, 1440p): R with ancestors and D with ancestors per view, pinned tight (within 10 %). ADR 0033's fractions (R at most 10 % of the compact mid slots, ground-1m D at most 6 %) hold (6.2 % and 1.8 %); the vertex-format fractions are 38 % (R of the mid slots) and 10.9 % (ground-1m D), pinned at 40 % and 12 %.
- **The manager is the streamer's front.** `ResidencyManager::begin_frame` degrades the wants, calls `begin_frame_wants` and resolves the caller's original draw tiles (a replaced D tile shows its nearest resident ancestor). The renderer asks `Streamer::slot_of` and executes the placement with `upload_at`.

- **Timing.** The slot a job reserves at dispatch is deterministic; the frame at which a cancelled or failed job's slot is given back follows its completion, as the resident set already did. Images do not depend on placement (REND-013).

## Risks

- Reserving at dispatch makes a full pool throttle generation instead of generating tiles that cannot be kept. With R fitted by `degrade` the pool always has victims for draw requests; a want set that is not fitted (a caller using the streamer directly) can block, which `StreamStats::blocked` reports.
- The vertex pool is allocated whole (27.5 MB at cells 32) when the first level 0-2 tile is uploaded.
