## Decisions

1. **One number for the pool and the limit.** `GenWorkers { workers, ahead }` builds the pool (`workers` threads) and applies `max_in_flight = workers`, `queue_ahead = ahead` to a `StreamConfig`. The app no longer states a pool size and a limit separately. Default `workers` is `available_parallelism()` (20 on Rasierklinge) because the dive is generation-bound and the store scales to about 20 threads (7b); the plan worker has its own pool and scoped threads, so the tile threads are not the planner's. Cores kept free for the frame thread are F8's question: `--gen-workers N` is the knob.
2. **Refill without waiting for the frame boundary: queue ahead, not a worker-side callback.** The streamer is single-threaded and frame-driven (CON-04, CON-14). A completion-triggered refill from the worker would have the worker choose the next request from the shared queue, so the request order would depend on thread timing. Instead the scheduler hands over `queue_ahead` jobs more than there are workers, in queue order, at the frame boundary; the pool's FIFO gives them to workers as they free up. The order of requests stays a pure function of the wants, the resident set and the job limit; it does not depend on the spawner or the thread count. Cost: the choice of the next `queue_ahead` tiles is committed up to about one job duration earlier. The priority cost is bounded: a draw-set request that arrives behind a full queue waits for at most `queue_ahead` dispatches. A queued job holds its slot and is cancelled like any other (its closure checks the token at its start), so a teleport wastes nothing but the queue entries. With `queue_ahead = workers` a worker gets at most one extra job per frame interval: enough while D is at least about T/2; `--gen-ahead` raises it for cheaper tiles.
3. **Same limit, same decisions.** `dispatch` and `make_room` use `job_limit() = max_in_flight + queue_ahead`; configurations with `queue_ahead = 0` behave exactly as before, so the pinned scheduler digests are untouched (the equivalence scripts name `queue_ahead: 0`).
4. **Tier A models the machine.** `TimedSpawner` runs N workers with a duration per job on a model clock that moves by frames; a freed worker takes the next waiting job at once, as a pool does, while the streamer sees completions at frame boundaries only. The test controls (`with_ahead(0)`) show the old refill at 54% of N / duration, so a regression of the cap or of the refill shows as lost throughput.
