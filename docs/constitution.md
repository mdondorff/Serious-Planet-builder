# Constitution

**Status:** v1.7, 2026-11-11 (simulation architecture: CON-04 to CON-08, CON-11, CON-13 to CON-15, CON-18 to CON-23, CON-25 to CON-27 refined; CON-28 to CON-31 added; ADR 0116). Earlier amendments, each by the owner: v1.1 ADR 0010, v1.2 ADR 0017, v1.3 ADR 0035, v1.4 ADR 0043, v1.5 ADR 0078, v1.6 ADR 0077. v1: 2026-10-09. Owner: Matthias Dondorff.

This file holds the project's non-negotiable rules. Every rule has an ID and a verification tier (A pure, B CPU oracle, C pixels, D human; see `openspec/specs/testing`). Rules are deliberately short; the reasoning lives in the ADRs and in `docs/background/architecture-report.md`.

**Precedence:** this constitution > accepted ADRs (`docs/adr/`) > OpenSpec specs (`openspec/specs/`) > background docs (`docs/background/`, frozen, non-normative). When two sources conflict, the higher one wins and the lower one is corrected (background docs are never corrected; they are history).

**Amendments:** only by the owner. Claude may propose an amendment (as an ADR with status "proposed" that names the rule) but never edits this file on its own.

## 1. Architecture and layering

- **CON-01** One binary with three run modes (editor/viewer, `generate` headless CLI, `test-render` headless harness) built on shared library crates. *Verify: A* (all modes build and start in CI).
- **CON-02** Crate dependencies point downward only: `core → world-def → generators → cache → streaming → frame → render → editor → app`. `core`, `world-def`, `generators`, `cache`, `streaming` and `frame` compile without any graphics crate. *Verify: A* (CI builds them with no GPU dependency in the tree).
- **CON-03** The renderer executes a `FramePlan` and makes no decisions about what to draw. Terrain node selection (which nodes, which LOD, morph factors) is a pure CPU function in `frame`. GPU-side culling is allowed only for instances and only behind a differential test against a CPU reference. *Verify: A, C.*
- **CON-04** Streaming and scheduling code receives time, I/O and task spawning through injected interfaces, so it runs deterministically in tests with fakes. Parallel and asynchronous algorithms are allowed; scheduling never alters an authoritative result. *Verify: A.*

## 2. World description and generation

- **CON-05** The WorldDefinition is the authoritative description of the world: authored inputs, body properties, simulation profile and edit history. Canonical derived state is reproducible from its declared inputs, algorithm versions and dependency identities, and may be reused when its complete dependency identity matches. Runtime representations (tiles, meshes, textures, instances) are disposable caches. *Verify: A* (`cache-verify`).
- **CON-06** Generation and simulation computations are pure functions of their declared read-set identity, algorithm and implementation versions, computation-domain identity (planet, region, partition, catchment, tile or point) and any explicit profile or seed. A pure computation need not be spatially local. Inputs are read only through a read-recording context; no undeclared global state, wall-clock time or unseeded randomness. *Verify: A.*
- **CON-07** Within one cache identity, each authoritative field has exactly one selected implementation, and the CPU implementation is canonical (CON-28). Preview, production, reference and new-version implementations are allowed under distinct, explicit identities with declared equivalence guarantees. An approved GPU implementation of a field matches the CPU within CON-14's tolerance. A *field* is data that a generator produces, that the cache stores or keys, or that CPU systems (collision, picking, placement, anchors) or other fields read; data the GPU derives only for display is presentation data, not a field (CON-14). *Verify: B.*
- **CON-08** Generation is staged, with declared dependencies between stages. Stages may run globally, regionally, over dynamically defined domains or over spatial partitions. A partition is an execution and storage strategy, not an assumption of independence: its boundary conditions and cross-partition dependencies are defined, and it preserves the canonical result (CON-30). An iterative stage may read declared outputs of its own earlier iterations under a versioned algorithm with a fixed iteration count or deterministic termination; other cycles are prohibited. Spatial locality is demonstrated, not assumed. *Verify: A, B* (metamorphic tests: border agreement, partition invariance, coarse/fine agreement).
- **CON-09** Authored content is stored separately from the procedural base, anchored in geo-coordinates, and records the `generator_version` and definition hash it was authored against. Surviving generator changes is a nice-to-have; the guaranteed options are version pinning and freeze/bake. *Verify: A.*
- **CON-10** The WorldDefinition file format has its own schema version and tested migrations, independent of `generator_version`. *Verify: A* (fixture files from older versions load).

- **CON-28** Authoritative world generation and simulation run on the CPU. GPU work may derive presentation data but never influences authoritative terrain, hydrology, erosion, basin or channel state; an exception needs an ADR and the owner's approval. *Verify: A, B.*
- **CON-29** Incremental generation and simulation produce the same canonical result as a fresh build from the same WorldDefinition, edit history, profile and implementation versions. A cached result is reused only when its complete dependency identity matches; otherwise it is recomputed. *Verify: B.*
- **CON-30** Spatial partitioning, chunk boundaries, execution order and thread scheduling do not change canonical results. A partitioned algorithm is validated against a canonical unpartitioned reference or a defined equivalent. *Verify: B.*

## 3. Numerics and precision

- **CON-11** Authoritative positions are float64 in the planet-fixed frame. Geometry (vertex positions, depth, anything that places a pixel) reaches the GPU only as tile-local or camera-relative float32 values, and no shader computes geometry from values of planet-radius magnitude. Presentation shading (CON-14) may use such values when its declared bound, including temporal stability under camera motion at 1 m altitude, is tested at the worst case. This is a geometry rule; the precision of simulation fields is set by their numerical contracts in the specs. *Verify: A, C* (precision test at 1 m altitude, far from the origin; for presentation shading, its declared-bound test).
- **CON-12** Depth uses reversed-Z with a 32-bit float depth buffer and an infinite far plane. *Verify: C.*
- **CON-13** Precision budget: render jitter < 0.25 px at 1 m camera distance anywhere on the planet; tile-vertex quantization ≤ 1 mm at the finest LOD; geo-anchor round-trip error ≤ 1 mm. These are rendering and anchor budgets, not precision requirements on simulation fields; the tests state their camera and geometry scenarios. *Verify: A, C.*
- **CON-14** Determinism: authoritative CPU generation and simulation are bit-exact across runs, thread counts, partitionings and the supported Windows and Linux x86-64 builds, including fields, graphs, topology, hydrology, basin and channel state and canonical serialization; fresh and incremental builds agree (CON-29). Hashing and noise lattices are integer-based; transcendental functions use the approved deterministic implementation (today `libm`, ADR 0010); no fast-math; floating-point contraction and reductions are controlled. Parallel execution is allowed when the logical reduction order, and so the result, is independent of scheduling and thread count. The guarantee is tested on the supported targets, not inferred from the mechanism. An approved GPU implementation of a field agrees with the CPU within a mixed bound `|Δ| ≤ max(rel·|v|, abs)` stated in the field's spec (heights: rel 1e-6, abs 1 mm; normals: 0.01°; masks: abs 1e-4). Neighbouring tiles in one cache share one `implementation_id`, so CPU and GPU tiles never meet at a seam. The CPU/GPU bounds apply to fields (CON-07). Presentation data (shading normals and their stored encoding, detail below the finest level, lighting, atmosphere, water surface motion, emission, blending, morphing) has no CPU twin: each such attribute states its class and its own precision bound in its spec, verified by tests and golden images; CON-11 and CON-13 still apply. An attribute that becomes an input to a field or a CPU system needs a CPU reference and an ADR first. *Verify: A, B* (CI compares tile hashes across operating systems).
- **CON-15** Geo conversions go through a `ReferenceSurface` interface (sphere first), used wherever body geometry affects coordinates, areas, distances or normals. Geo-coordinates are the serialization format for authored anchors. *Verify: A.*

## 4. Verification

- **CON-16** Every requirement in `openspec/specs/` has a trace ID and a declared verification tier. Every automated test cites the requirement ID it covers (`// spec: COORD-003`). `cargo xtask spec-lint` enforces both. *Verify: A.*
- **CON-17** Verify at the cheapest tier that can falsify the requirement. Tests are deterministic; a flaky test is fixed or quarantined with a tracking entry, never retried silently. *Verify: A.*
- **CON-18** Every substantive visual system or feature (terrain, hydrology, materials, LOD, atmosphere, water; not every UI element) ships with a debug view and at least one tier-C test. Golden images are approved ("blessed") by the owner, or by an agent under the owner's policy in ADR 0017; everything that policy escalates waits for the owner. *Verify: C, D.*
- **CON-19** Every visual bug gets a repro bundle (camera path, definition hash, generator version, settings, and the adapter where the bug depends on it) that `cargo xtask repro` replays. *Verify: A.*
- **CON-20** Count-based budgets (draw calls, triangles, resident tiles, upload bytes, VRAM allocated) are asserted in tests on any adapter. Time-based budgets are measured only on the reference machine, using the performance-harness protocol. The same discipline holds for build and simulation budgets (peak build memory, store size, temporary storage), stated in the performance specs. *Verify: A, C.*

## 5. Performance gates

- **CON-21** Reference machine: Rasierklinge (RTX 3080 Ti Laptop GPU, 16 GB VRAM), charger connected, fixed performance power profile, discrete GPU confirmed by the harness. Targets at 1440p internal resolution: 60 FPS (16.6 ms) median, p99 ≤ 20 ms on the standard flight paths; VRAM within the active cap (8 GB mid-range tier, 14 GB high tier); runtime RAM ≤ 8 GB (viewer and editor; build and re-solve memory have their own budgets in the specs); GPU uploads ≤ 2 ms per frame. *Verify: C* (performance harness).
- **CON-22** Streaming never blocks a frame: some LOD is always available for every visible node (parent-first requests), also at startup and after cache invalidation. *Verify: A* (dive test with fake I/O), *C*.

## 6. Process

- **CON-23** Decisions are recorded as ADRs. An accepted ADR is historically immutable: its decision and original evidence are not rewritten. A correction, an invalidated assumption or superseding evidence is recorded in a linked amendment, errata or superseding ADR that names the original claim. Maintenance that keeps the meaning is allowed and traced by a `Maintained:` line (ADR 0078): status, moved links, spec-owned values, renamed domain terms, errata markers. Only the owner accepts decisions and amendments.
- **CON-24** OpenSpec holds the current specs; work happens as OpenSpec changes that are archived when done. Background docs are frozen and non-normative.
- **CON-25** All supported build, test, generation and repository-maintenance workflows are exposed through `cargo xtask`. Scripts may implement narrowly scoped integration or automation, but never define a competing workflow or bypass xtask.
- **CON-26** Development is Windows-native (MSVC toolchain); Linux is covered by CI, which runs the determinism tests, not only a build. WSL is not part of the workflow.
- **CON-27** Third-party code, dependencies, assets and datasets have recorded provenance and compatible licence terms (ADRs, `cargo deny`). Adopted algorithms record their sources where appropriate; known patent, contractual or licence restrictions are reviewed before adoption. Incompatible code or assets are not adopted.
- **CON-31** No requirement, test, gate or accepted decision is weakened, deleted, bypassed or reinterpreted to make an implementation pass; a conflict is raised as a proposed change with evidence for the owner. Reports distinguish tests run and passed, tests written but not run, tests not written, and results inferred from other evidence.
