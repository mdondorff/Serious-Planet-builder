# Learnings, M4 (milestone scope)

## 2026-10-15 The frustum cut removes almost nothing near the ground, and the eroded field's plan is not the reference field's plan
What happened: SPIKE-05 (docs/spikes.md). (1) `select_impl` pads every node's sphere by the global `max_height_m` (9 km or more) before the frustum test, so at ground-1m the draw set is 8,763 nodes against 10,751 for the position-based set (81 %); a CPU depth pass shows 96.2 % of the drawn triangles and 87 % of the drawn tiles produce no visible pixel, and a frustum test with each tile's own bounding sphere would keep 2,913 tiles and lose none that is visible. The 5.4 triangles per pixel of the review are hidden terrain. (2) `plan_terrain_cached` over the eroded field on the 16384 bake takes 20 ms warm at ground-1m (selection alone 5.8 ms; the rest is the per-node tile-centre height and mesh key), 180 ms cold, and 5-7 s at orbit and 2000 km (52 and 429 nodes; the selection takes under 2 ms): the perf windows plan the reference field, which reads no bake. (3) `StoreSource` holds one mutex per lattice read: tile generation over the store runs at 22 tiles/s on 20 threads against 113 on one (1,217 on 20 with an in-memory bake).
Assumption it changes: LOD-007 (frustum cut), the perf windows' plan budget (CON-21, 8 ms warm) as a statement about production terrain, ADR 0026 point 7 (the reader), ADR 0033's hand estimates (residency set 3-6x the draw set: measured 1.23x at ground-1m).
Proposed follow-up: a change that culls with per-tile height bounds; origin and mesh key stored per resident tile; a lock-free or per-thread block cache in `StoreSource` before the scheduler is measured; the perf scenes plan the world's field (M4 item 7); ADR 0032 reports plan time as its own term.

## 2026-10-15 The draw plan's cost is the per-node origin height, not the mesh key; at altitude it is the store's block cache
What happened: M4 item 7a ablation (`cargo run --release -p planet --example plan_ablation -- --store DIR --global-res 16384`; eroded field over the stored 16384 bake, cells 32, tau 6, 2560x1440, ad hoc, single thread, a counting `HeightField` wrapper; ms, warm = the same request again). Per view, the whole plan against its parts: selection alone, the per-node `field.height(centre)` for the tile origin, and `MeshKeyer::key` for every node.

| view | nodes | selection warm | origin heights | mesh keys | plan warm |
|---|---|---|---|---|---|
| ground-1m | 8,763 | 4.4 | 14.9 | 0.24 | 17.8 |
| ground-200m | 4,498 | 2.0 | 7.5 | 0.13 | 9.3 |
| low-2km | 2,625 | 1.2 | 4.1 | 0.07 | 5.3 |
| aerial-20km | 1,106 | 0.5 | 1.6 | 0.03 | 2.2 |
| aerial-200km | 655 | 0.3 | 695 | 0.02 | 693 |
| high-2000km | 429 | 0.2 | 5,606 | 0.01 | 5,574 |
| orbit-20000km | 52 | 0.04 | 6,206 | 0.00 | 6,176 |

Field calls per plan: `height` once per node (8,763 at ground-1m), `height_bounds` none warm (the selection cache serves them; 13,448 cold), `inputs_hash` 2 (the batch keyer and the cache key), `read_records` 0. (1) The mesh key is not the cost: `ErosionField` does not read cells, so the keyer hashes one constant per tile (0.25 ms for 8,763 nodes, 0.00-0.03 ms at altitude). The SPIKE-05 inference (coarse tiles hash every bake cell of their footprint) was wrong. (2) The warm cost at ground levels is the origin height, 1.7 us per node by the eroded field's per-sample cost: 14.9 of 17.8 ms. (3) At altitude the origin height of a coarse tile costs about 120 ms per node (52 nodes 6.2 s; 429 nodes 5.6 s; 655 nodes 0.7 s) even when warm; the same code over an in-memory 1024-cell bake plans orbit in 0.12 ms. A coarse tile's centre sample (base elevation and the gradient stencil) reads lattice blocks far apart, and `StoreSource`'s 16-block LRU of up-to-16 MB blocks cannot hold them across 52 to 655 locations, so every sample decodes blocks again: that is the store source (item 7b), not the planner. Caching the origin height per tile across plans removes it from every warm plan; a cold plan (a teleport) still pays the decodes. (4) Cold selection (59-250 ms at ground levels) is the first `height_bounds` per tile, also store reads.
After 7a (same tool and setup, warm plan, ms): orbit 0.04, high-2000km 0.23, aerial-200km 0.37, aerial-20km 0.56, low-2km 1.29, ground-200m 2.30, ground-1m 4.69 (17.8 before), north-pole-1km 1.28, cube-corner-1km 2.03, face-edge-1km 1.89: all within the 8 ms budget. Cold plans are unchanged (orbit 6.3 s, ground-1m 21 ms plan after 175 ms selection).
Assumption it changes: SPIKE-05 / `docs/spikes.md` point (2), "the mesh key of the coarse tiles"; item 7a's plan to bound a coarse tile's key cost (there is none to bound; no key derivation changes, so no ADR).
Proposed follow-up: 7a caches the origin height and the mesh key per tile in the `SelectionCache` (same invalidation key, plus `cells` for the mesh key); 7b's block cache is what a cold altitude plan needs.

## 2026-10-15 StoreSource: the mutex was the rate, the block count is the cold plan, and no 0.5 GB cache holds the altitude working set
What happened: M4 item 7b ablation (`cargo run --release -p planet --example store_blocks -- --store DIR --global-res 16384 --part plans|rate|decode`; eroded field over the 16384 store, cells 32, tau 6, 2560x1440, ad hoc, a fresh `StoreSource` per row; a recording wrapper counts lattice reads and distinct 1024-cell blocks). Cold = fresh `SelectionCache`; "blocks-warm" = the same request again with a fresh `SelectionCache` (only the store's block cache is warm). Before (branch base 2941c5f): orbit-20000km 6134 ms cold / 6204 blocks-warm (52 nodes, 938 reads, **188 distinct blocks**); high-2000km 4857 / 4851 (429 nodes, 7,738 reads, **144 blocks**); aerial-200km 658 / 608 (655 nodes, 11,424 reads, 20 blocks); aerial-20km 259 / 90; low-2km 234 / 133; ground-200m 208 / 171 (2 blocks); ground-1m 297 / 265 (8,763 nodes, 4.3 M reads, 2 blocks). Findings: (1) A block costs 33 ms to fetch and decode (17 ms to read and CRC the 8 MB record, 16 ms to LZ4-decode and unshuffle into 16.8 MB of samples): 188 blocks x 33 ms = the orbit plan. (2) The coarse tiles' reads are not on a coarse sub-lattice: a histogram of the trailing zeros of i|j over the orbit view's reads (both passes) is 62 % odd, 25 % one zero, 5 % two, none between 3 and 10, so a decimated copy of each block (every 8th vertex) would serve almost none of them; about 5 reads per block, 3.6 blocks per node. (3) The working set of orbit is 188 x 16.8 MB = 3.2 GB and high-2000km 2.4 GB, six times ADR 0033's 0.5 GB proposal for bake blocks (31 blocks of 1024 cells): the old 16-block LRU thrashed (warm = cold), and a 31-block cache thrashes the same way at orbit and high; only views up to about 30 blocks (aerial-200km: 20) benefit (658 to 2 ms warm). So a block cache alone cannot make a cold plan at orbit fast within the budget; the lever is cost per block. (4) The pack record read took the pack file's mutex for seek plus read, and CRC-32C ran bytewise (about 500 MB/s): 17 ms for 8 MB. The mutex of `StoreSource` made 20 threads 5x slower than one (20 tiles/s on 20 threads, 111 on one).
After (same tools): CRC-32C slicing-by-8, positional pack reads, one-pass decode: fetch 7 ms + decode 13 ms = 20 ms per block (33 before); `StoreSource` reads through a thread-local pin of the last block and a byte-budgeted shared LRU with one decode per block (STRM-014, 31 blocks of 1024 cells). Cold plans: orbit 3.85 s, high-2000km 2.97 s, aerial-200km 339 ms (2 ms with its 20 blocks resident), aerial-20km 167, low-2km 161, ground-200m 151, ground-1m 222 ms. Tile rate (eroded, cells 32, ground-1m draw set): 152 tiles/s on one thread (111 before), 1,000-1,190 on 20 threads (20 before) against 1,207 in memory in the same session: 83-98 %; 320 tiles at 1, 4 and 20 threads are bit-identical to each other (hash of every mesh vertex and key) and the tier A test also compares them to the in-memory bake.
Assumption it changes: SPIKE-05 point 3's "a lock-free source" would fix both rate and cold plans: it fixes the rate; a cold plan at orbit or 2000 km is 144-188 block fetches whatever the cache, and 20 ms each leaves 3 s. SPIKE-05's 400 s to fill the ground-1m draw set through the store now follows from the tile rate (about 8 s on 20 threads).
Proposed follow-up: a teleport at altitude should not plan cold on the frame: evaluate the origin heights of a cold plan's new nodes on worker threads (pure function of the tile, so thread-count independent) or keep a persisted coarse summary of the field per tile (an ADR: a new derived product); otherwise ADR 0032's completion must exempt the teleport frame.

## 2026-10-15 The global height pad kept four tiles in five near the ground; three tests had leaned on it
What happened: M4 item 7c. Testing the frustum against each tile's own height-bounds volume (plus skirt depth) instead of `max_height_m` cut the standard-view draw sets from 8,687 to 2,897 nodes at ground-1m (aerial-200km 645 to 630, low-2km 2,561 to 1,279). The SPIKE-05 depth pass (now `crates/frame/tests/support/depth_oracle.rs`, tier B `oracle_frustum_cut.rs`) finds 1,108 tiles with a visible triangle at ground-1m: the remaining 1,800 are occlusion, which stays out of scope (CON-03). Plans got cheaper too (ad hoc, reference field: cold ground-1m 39.7 to 15.3 ms, warm 6.0 to 2.2 ms).
Assumptions it corrected: (1) `height_aware.rs` assumed the leaf under a ground camera is always in the plan; the pad kept it, the tight cut drops it when the camera looks away from the nadir (it is outside the image). The test now takes the leaf from the selection without a frustum and checks that a leaf missing from the plan has no vertex in view. (2) `dive.rs` needed a queue to cancel from: with the smaller draw set 10 jobs per frame drained it, so the scenario runs 6 per frame (same pressure, 5 cancelled). (3) the TEST-011 pins and two plan snapshots were declared changes.
Proposed follow-up: none; the residency set stays position-based (ADR 0031), so these dropped tiles are still resident.

## 2026-10-15 `test fast` had regressed to 32-53 s: three sweeps and a spinning watcher (test-fast-regression)
What happened: `cargo xtask test fast` read 32 s on a quiet machine at the base of this change (43-53 s in verifier runs), against 6.2 s after #108. The tests added since were correct but single-threaded or redundant: `frustum_cut` built a tile mesh for every checked tile of every camera (the four heading variants of a view cut almost the same tiles: 36,000 checks, 15,600 distinct tiles on the steep field; 30 s and 14 s), `height_aware` steep checked ten independent views one after the other (8 s), `residency_headroom` opened the same 256-cell bake twice, and the budget watcher of `concurrent_source` spun on a core for the whole test. Per-test times from a 20-thread run are inflated by contention (the same test read 1.7 s alone and 6-7 s in the run; the sum of reported times was 181 s against 58.7 s of CPU time with the run pinned to one core: `Get-Process` affinity 1 and `-j 1` gives each test's real cost). The run is CPU-bound at about 6 times a single core (14 cores, hybrid), plus about 1 s of cargo and nextest listing outside the reported test time, and the same code read 7.9 to 9.5 s of test time within one session.
Fix: the cameras and views run on scoped threads, distinct tile meshes are built once, the bake is opened once, the watcher yields. The vertex-per-plane sweeps were still the largest cost, so their exhaustive density moved to tier B (`oracle_frustum_cut_sweep.rs`) and tier A keeps a slice (every eighth dropped tile of every camera; on the steep field two of the four headings of each view); LOD-007 keeps its tier-A evidence. `test fast` now prints the five slowest tests (nextest JUnit report) and the existing warning above 10 s.
Assumption it changes: "a test that is correct and fast alone is fast in the tier". The tier is CPU-bound, so the sum of CPU time (not the longest test) is what a new test costs: add a test's CPU time to the budget, and check it with the one-core method above.
Proposed follow-up: Windows Defender real-time protection is on and every test is its own process (563 of them); an exclusion for `target/` on the owner's machine may lower the fixed cost (not measured: it needs administrator rights).

## 2026-10-15 A cover that bounds distance by the global height range descends to level 26 (frame-pipelining)
What happened: the first `cover_selection` split a tile while a geometry-only lower bound of its distance (reference sphere, less the global `max_height_m`, 9 km or more) was below the level's split distance. With every tile resident and the camera 3 km up, every tile within 9 km of the camera has a bound of zero, so the walk went down to the finest level over a disc of that radius (millions of tiles; a test ran for minutes). The same looseness hangs any test field that does not override `height_bounds` (the default is the global range) while the planner needs tight per-tile bounds. The cover now measures from the camera to the tile's resident origin (known from the mesh, no field read) less the tile's radius.
Assumption it changes: ADR 0032 point 5 ("the selection restricted to resident tiles, which evaluates no field") is right in outcome but "the selection restricted" cannot reuse the selection's distance bound; the cover has its own criterion (STRM-016).
Proposed follow-up: none; new test fields delegate `height_bounds` to the reference field.

## 2026-10-15 R is cheap on the plan's cache because a resident tile carries its own origin (residency-wiring)
What happened: #132 deferred wiring R because it looked like a second cold evaluation. R (position-only selection plus ancestors) reads only tile geometry and height-aware volumes, which the plan's `SelectionCache` already holds for every tile its frustum cut visited; it never needs the per-tile origin height or mesh key (those the expensive part at altitude), because the origin and key of a resident tile come from its mesh. On a counting field R after the plan adds zero `height` calls; a repeat or a turn adds zero `height` and `height_bounds` calls. What R does add is the volumes (height bounds) of tiles outside the frustum, evaluated serially after the plan is published. Unmeasured: that cost at altitude and the O(R) per-frame fit in the manager (needs a perf window).
Assumption it changes: "R from the worker is a second cold evaluation" (#132 deferred list) holds only for the volumes of the tiles outside the frustum.
Proposed follow-up: the perf window reports plan_ms with and without R, and scheduler_ms at the largest R; cache the fit per change of the wants if it matters.

## 2026-10-15 fallback tiles live in the renderer's half of the vertex pool
What happened: the residency manager reserves a main slot when it dispatches a tile, before the tile is built; whether a finest tile falls back to the vertex format (CON-13, relief over 65.535 m) is known only after. ADR 0033 points 3 and 5 say the 512-slot vertex pool takes the fallback tiles, as if the manager placed them. The compact renderer instead splits the pool: the bottom 256 slots are the manager's (levels 0-2 need at most 126), the top 256 are the renderer's fallback region with its own free list and frames-in-flight retirement, and the manager's main slot for a fallback tile stays empty while it lives (8.7 KB once per fallback tile; zero on the standard views). A fallback beyond the region fails with `PoolFull { Vertex }` and the tile id.
Assumption it changes: ADR 0033's single vertex pool with one discipline (same 512 slots and 28 MB in total; the manager's part is 256).
Proposed follow-up: part 3 handles the error; if the owner wants the manager to place fallbacks, that is a proposed ADR (the manager would need the format before dispatch).

## 2026-10-15 upload budget: whole tiles, and what the 1 MiB counts (sonnet-explorer)
ADR 0033 point 9 says a full ground-1m fill (8,763 compact slots, 77 MB) takes 74 frames at the 1 MiB cap. That divides bytes; the cap is paid in whole tiles (118 compact tiles of 8,840 B per frame), so it is 75 frames, and the vertex format (19 tiles of 53,724 B per frame) takes 462. The cap is on tile data; node records (614,164 B at ground-1m) are reported as their own line (`node_bytes`) and `UploadBudget::node_records_in_cap` folds them in by configuration if the perf window shows tiles plus records over 2 ms. The value is provisional (ADR 0033 point 9 proposed). `upload_ms` also carries the ranking of the waiting tiles (class sets rebuilt when the wants change), so read it during fills in the perf window.
Assumption it changes: ADR 0033's 74 frames.

## 2026-10-15 the 4.5-minute "teardown" was the root load; teardown was 9-14 s and a cancelled tile is now discarded (sonnet-explorer)
What happened: measuring the teardown of a perf case over the 16384 store (teardown-cancellation). `Rig::new` spent 243 s in `load_roots_blocking` (six level-0 tiles read one after the other from a cold store; every scene opens a fresh reader and pays it); the teardown proper was 9-14 s, the eight tile jobs in flight, each one uninterruptible stage. The streamer had no Drop, so nothing was cancelled.
Assumption it changes: ADR 0031 point 3 says a tile that completes anyway goes to the persistent cache. With `MeshSource::load_staged` a cancelled tile stops at its next height sample and is discarded unbuilt, so nothing is cached; the ADR sentence holds only for sources without stage boundaries.
Follow-up: the 243 s cold root load (parallel roots or a coarse summary) is open and costs every scene its start.

## 2026-10-15 detail lag is judged against a fresh plan of every frame's camera; doing so shows the cover is coarse while turning (sonnet-explorer)
What happened: fresh-plan-lag. The old coverage guard (a gated lag judged on fewer than half the frames is "not measured") existed because the lag was taken against the pipelined loop's own newest plan, usable only within 0.5 degrees. Now `detail_lag` judges every frame against `plan_terrain` of that frame's camera (the synchronous plan), from a post-pass over the recorded f64 poses and drawn tile ids, so no frame lacks a target and the guard is gone (a missing pose or lag is OVER, not "not measured"). Doing it on the fakes of the managed loop showed two things the stale-plan comparison hid. (1) A camera that turns more than 0.5 degrees per frame draws the cover of the resident set, which stops at levels 3-8 where the selection wants 7-13 (every in-view child must be resident and the cover's culling is looser than the plan's, so a non-resident out-of-plan child stops the descent): a lag of up to 10 levels per frame for as long as the turn lasts, although the whole residency set R is resident. (2) Under a usable stale plan a newly revealed edge node has nothing drawn at or above it for a frame (reported as `uncovered`, counted as level + 1 in the lag, a sliver).
Assumption it changes: that "rotation-only at the settled state has lag 0" follows from R being resident; it holds for a still camera, not for one that turns faster than the stale-plan rule. The look scenes' gated rule (lag 0) will report OVER on a real run until `cover_selection` follows the plan's culling or the stale rule is widened.
Proposed follow-up: a change to `cover_selection`/`draw_plan` (the architect decides); the perf window will show the size of it.
Also recorded (spec-guardian): this reads ADR 0032 point 4 ("the resident tile actually used, an ancestor if the node is missing") with two interpretations: a node covered only by drawn descendants has lag 0, and a node with nothing at, above or below it is "uncovered" (level + 1, reported, not the hard blank measure, which stays the draw's own count of nodes with nothing resident). Consequence: coverage of the fresh selection (ADR 0032's "a tile for every visible node" at the teleport) is reported (`uncovered nodes`) but no longer a hard gate; the architect decides whether it should be.

## 2026-10-15 the 243 s root load is block-cache thrash, not 40 s per root; six concurrent roots give 237 s -> 103 s (sonnet-explorer)
What happened: parallel-root-load. Measured over the real 16384-cell store (`store_blocks --part roots`, release, one machine run, OS file cache warm after the first pass). Per root, a fresh source with an unbounded budget: 7 s, 130,962 lattice reads (131,008 on faces 4 and 5), **320 distinct blocks and 320 decodes = 5,379 MB decoded per root** (16.8 MB per block; 256 blocks of its own face plus the neighbours across the edges); the six roots together touch **1,536 distinct blocks** (about 25.8 GB decoded if each were decoded once; the faces share almost nothing). With the default 512 MiB budget (31 blocks) the same roots read one after another take **237 s and 11,581 decodes** (7.5 times the distinct blocks): a root's reads are scattered over its whole face, so the LRU re-decodes constantly. Loading the six on a pool of 6 (`Streamer::load_roots_blocking`, new): **102.8 s, 18,147 decodes** (more thrash, since six roots interleave in one 31-block cache, but six decode streams at once). Vertices are identical (1,221 per root, same in both).
Assumption it changes: "each root touches most of its face's blocks, so ~40 s each" is right about the blocks but the cost is the re-decode of blocks evicted before the next vertex wants them, not the first decode (a root with room for its 320 blocks takes 7 s). Concurrency alone gives 2.3x, short of the 40-60 s goal.
Proposed follow-up: (a) a larger budget during the root load only, or the persisted coarse summary / lattice pyramid (needs an ADR; a level-0 tile does not need full-resolution blocks), (b) reordering a root's reads so they walk the blocks (generator change: numerics-reviewer), (c) sampling within one tile on the pool (the decode streams would rise from 6 to 20; skipped here, it needs the generator's per-vertex loop split). Tracked as a cold-start finding for the M5 viewer.

## 2026-10-16 The frame-thread scheduler rebuilds its whole working set every frame: 90% of 6 ms at a settled look is two rebuilds of |R| (scheduler-incremental, F2, STRM-005, TEST-018)
What happened: perf window 1 put the frame thread's scheduler column at median 9.5 ms (p99 10.6) at look-1m with zero requests. Ablation before any fix (`cargo run --release -p planet --example scheduler_ablation -- --scene look-1m`, in-memory 256-cell bake, eroded field, cells 32, finest level 22, 2560x1440; the managed loop with real plan worker, residency manager, upload budget and prefetch, a fake source and a counting sink; per-step timers were a temporary patch of `Streamer::begin_frame_wants` and `ResidencyManager::begin_frame`, reverted). Settled look-1m (D 672, R 11,493 resident, 200 frames at 16 ms): scheduler median 6.13 ms (this machine, not Rasierklinge), of which the manager's `degrade` (BTreeMap of R, pinned set, ancestors closure, merge pass) 2.23 ms (36%), the streamer's `needed` map (every tile of D and R walked up through all its ancestors: about 170k hash writes) 3.45 ms (56%), the `last_used` touch of every resident needed tile 0.28 ms (4.5%), the enqueue scan of `needed` against resident/in-flight 0.10 ms, resolving D twice 0.04 ms, completions, cancel scans, make_room and dispatch about 0. Nothing here depends on whether anything changed: the wants of consecutive frames are the same Vec (the loop rebuilds them only when the worker delivers a plan or R), yet degrade and `needed` are recomputed from scratch every frame. look-2km (D 1,013, R 6,362): 2.68 ms median, the same split. teleport-1m (landing, 2,376 requests): 8.4 ms median because the enqueue scan also re-keys every queued request every frame (2.09 ms: `queued_key.insert` then `queue.remove` and `insert` of an unchanged key for each of about 2,300 queued tiles); the other steps as at look. Not the cause: the sort/rank of waiting uploads (not in the scheduler column; empty at a settled look), clones of R (the loop clones the prefetch Vec only), cancelled-job scans (0.00), the ancestors walk of D alone (D is 6% of the work). The dive over its first 300 frames (R 1.3k) costs 0.28 ms median here; over the whole 40 s script (R 11.5k at the end, a backlog of 3,000 queued requests mid-descent) the old code measured median 5.65 / p99 7.44 ms: the same rebuilds, plus a re-key of the whole queue on every delivery. After the change (same example, same machine, release, software, no GPU, 16 ms pacing; ms median / p99 / max): look-1m 6.03 / 6.66 / 7.91 to 0.13 / 0.25 / 0.28 (the plan changes every frame, R never), look-2km 2.65 / 2.97 / 4.83 to 0.08 / 0.16 / 0.28, teleport-1m 8.17 / 9.40 / 9.68 to 0.17 / 0.31 / 3.8 (the one frame that takes R in: 11.3k tiles entering a layer and the queue), teleport-2km 3.89 / 4.48 / 5.33 to 0.17 / 0.31 / 2.6, dive 5.65 / 7.44 / 18.9 to 0.18 / 0.39 / 0.61. The real window measures the real number (Rasierklinge, the real tile source, 20 threads competing).
Assumption it changes: STRM-005/ADR 0031's "the scheduler works from the wants each frame" was implemented as recomputing every derived set each frame; the O(|R|) cost per frame was invisible while R was a few thousand tiles on the fakes (#127, #128) and decisive at finest level 22. It does not change ADR 0031's semantics; it changes how they are evaluated (derived sets follow the wants' changes, not the clock).
Proposed follow-up (done in `scheduler-incremental`, STRM-019): persistent per-class tile sets with closure counts updated from diffs of the wants, a class-change event stream (queue, cancel, eviction candidates), lazily built priority keys and a lazily ordered queue, `degrade` only when the closure could exceed the pool; work counters (tier A) assert a settled frame costs nothing and c changes cost O(c). What is left on the frame thread: the upload column's ranking of waiting tiles (F5), the loop's own rebuild of D from a delivered plan (O(|D|) per plan), one sequential pass over R when R is delivered, and keying the draw set once per plan delivered while draw requests wait (O(|D|)).

## 2026-10-16 A cold plan at altitude is the origin heights of its nodes, one block decode (20 ms) per block; 20 plan threads re-decoded half of them (cold-plan-origin-heights, F3, LOD-009, GEN-020)
What happened: perf window 1's worst dive plan was 9,384 ms and the descent lag 10.6 levels. The time is the origin heights above 200 km and it is the decode of blocks the origin height barely uses: 52 nodes read 938 lattice cells in 188 distinct blocks (18 cells and 3.6 blocks per node: the erosion stencil of a coarse node spans blocks), a block costs 9 ms to read and 12 ms to decode. The selection is 0-1 ms there (the height bounds of a wide cap are the global range, no lattice read) and 55-96 ms below 20 km (1-2 M reads inside 1-2 blocks). The hypothesis "block-cache thrash" was only half right: ONE thread decoded every block once (decodes = distinct blocks, 188), because the footprints of a cold plan's nodes hardly overlap; the batch (`heights`, one footprint gather) is no faster on one thread (3,725 against 3,911 ms). What thrashed was the 20-thread prefill: 352 decodes for 188 blocks at 20,000 km (536 for 345 at 5,000 km), partly from nodes sharing a block across thread chunks, partly (the larger part, found by counting after the batch was in) a `StoreSource` pin made for the epoch read BEFORE the decode: with 20 threads decoding at once the epoch moves with every insert, the pin was stale at once, the next cell of the same block went to the shared cache and found its slot evicted (a re-decode).
Fix: the plan evaluates the origin heights its cache lacks as ONE batch (`HeightField::heights_threaded`, `eval_gathered_threads`: footprint pass, distinct blocks dealt to the threads, one block per thread at a time, evaluation from the cell table in chunks) and `StoreSource`'s per-thread pin no longer expires with the eviction epoch (reading the epoch after the decode, tried first, still re-decodes for a cache smaller than the thread count). Bit-identical (tier A: plan == per-node evaluation for the ten standard views and five dive altitudes, 1 and 20 threads; decodes of a cold plan over a cache of ONE block == distinct blocks). The selection never reads an origin height, so one batch per plan (not one per level) was enough; taking an origin from a resident tile was not done (the plan is GPU-free and has no resident set; a cold plan has nothing resident).
The dive replayed the way the plan worker runs it (one cold source and cache, 20 threads, the next plan is for the camera at the time the previous job plus R ended; `--part dive`): before, the plans in flight were 1,230 ms (20,000 km, the first full plan), 3,945 ms (10,000 km, the worst), 315 ms (1,100 km), then 33 ms and below; after, 678-748 ms (first full plan), then 1,342-1,955 ms (13,700 km, the worst; two runs, the replay is timing dependent), 1,310 ms (6,400 km), 666 ms (3,100 km), 207 ms (2,100 km), then 20-40 ms (one block each) and 1-2 ms warm. The real window's 9.4 s is the same plan sharing the machine with the tile workers (8 decoding threads), the render thread and the scheduler, so expect about half of the ratios here, not the absolute numbers.
Floor: 188-345 blocks at 21 ms is 4-7 s of CPU; 20 threads reach 5.5x (memory bandwidth of 16 MB per decode and per transpose), so a cold plan at 20,000-2,000 km stays at 0.6-1.3 s (target 0.5 s not met). Going below needs decoding fewer cells than a block (a partial decode or a persisted coarse summary: an ADR; an origin height needs about 5 cells of a 1,025 x 1,025 block).
Tile generation per level (same tool, `--part tilegen`, compact tile under the dive site, cold source, 1 thread; the next tile east over the warm source): L0 6.6 s (320 blocks), L1 2.06 s (99), L2 0.74 s (35), L3 0.35/0.19 s, L4 0.21/0.09, L5 0.10/0.065, L6 0.061/0.020, L8 0.055/0.013, L10-22 0.03/0.011 s (1 block). The app's tile pool has 8 workers.
MODEL, not a measurement (arithmetic: 20 levels in 30 s = 1.24 s per level of descent, 0.81 levels per second; lag ~ 0.81 x (plan in flight + tile generation of the finest level's tiles over the pool; coarser levels assumed resident); tile costs above, mean of cold and neighbour for L3+; the pool as 5 and 8 effective workers): 20,000 km plan 0.7 s + tiles of L2 (52 x 0.74 s) 7.7/4.8 s -> lag 6.8/4.5 levels; 5,000 km plan 1.1 s + L4 (234 x 0.15 s) 7.0/4.4 s -> 6.6/4.4; 2,000 km 0.3 s + L6 0.97/0.60 s -> 1.0/0.7; 500 km 0.0 + L8 0.79/0.49 s -> 0.7/0.4; 200 km 1.15/0.72 s -> 0.9/0.6; 20 km 0.91/0.57 -> 0.8/0.5; 2 km 0.1/0.07 -> 0.1; 200 m 0.34/0.21 -> 0.3/0.2; 1 m 0.90/0.56 -> 0.7/0.5. Plan time is no longer what limits the dive below 2,000 km (0.0-0.3 s per plan); above it, the plan (0.7-1.3 s) and above all the generation of the coarse tiles (L1-L5 at 0.1-2 s each, 5-8 s for the finest level of a band) do: by this arithmetic the descent lag stays above 4 levels for the first ~7 s (20,000-3,000 km) and within about 1 level below. The mean over the descent will therefore probably stay over the budget of 1 without pre-filled coarse levels (the owner's decision, not changed here); worst 3 is not reachable from a cold start by plan time alone (the first plan alone is 0.7 s = 0.6 levels, the first level-2 tiles 4.8-7.7 s).
Assumption it changes: 7a/7b's "the origin height of each node is the cost of a cold plan" is right about where the time is, but the cure is not block ordering within one thread (already 1.0x decodes there) but parallel block reads without re-decodes; GEN-020's "decodes equal distinct blocks" holds for the plan only with the pin fix. The 20-core count in the replay also overstates a window where tile workers compete for the cores.
Proposed follow-up: if the window still shows plans of seconds at 20,000-2,000 km, a coarse summary (the planner's ADR: a level of the lattice pyramid, so that a coarse node reads kilobytes, not 188 blocks) is the lever; pre-filling coarse levels at start (the owner's decision) removes the first-plan wall; a larger block cache for coarse bands does not help a cold plan (distinct blocks, each once).

## 2026-10-16 The dive's 240 tiles/s is the pool of 8 refilled once a frame, not the generation rate: 8 workers x 2 frames per 18 ms job (dispatch-throughput, M4 fix F6/window 2, STRM-005, STRM-020, TEST-018)
What happened: perf window 2 (RTX, 16384 store) showed `in_flight` exactly 8 in every dive frame and 4 dispatches per frame (1,200 per 300 frames, 240 tiles/s) against the 1,000-1,190 tiles/s the store sustains on 20 threads; the request queue grew to 8,900 and the detail lag stayed at 3.5-14 levels below 2,000 km.
Where the numbers come from (read from the code, then reproduced on a model): (1) the 8: the app builds the tile pool as `ThreadPool::new(threads.clamp(2, 8))` (`pipelined.rs`, `scheduler_ablation`; 8 threads on this 20-thread machine) and sets `StreamConfig::max_in_flight: 8` beside it (two separate magic numbers, `pipelined.rs` and `skeleton.rs`'s `streamed_meshes`, which has a pool of 4 and a limit of 8). The plan worker has its own `ThreadPool::new(1)` plus scoped threads, so the tile threads are not the planner's. (2) The 4 per frame: the scheduler learns of a completion only in `collect` at the start of `step`, once per frame, and `dispatch` fills `in_flight < max_in_flight` only there. A job of D ms on one of 8 workers is therefore replaced at the first frame boundary after it ends. With a frame of T = 16.7 ms and a job of 18 ms (20 threads / 1,100 tiles/s) every job occupies a worker for two frames: 8 jobs per 2 frames, 4 per frame, 240 tiles/s, independent of how many tiles wait. `dispatch` itself already refills every free place each frame; no per-frame dispatch limit exists. In general the rate is N / (ceil(D/T) x T), which is 54 % of N/D at D = 1.08 T and approaches N/D only for D far above T.
Model (`TimedSpawner`, N workers, 18 ms a job, frames of 1/60 s, the real scheduler, a held demand of 5,000+ tiles): refilled at frame boundaries only: N=4 120, N=8 240, N=20 600 tiles/s against N/D of 222 / 444 / 1,111. The N=8 line is the window's measured 240 tiles/s.
Why tier A did not catch it: the managed-loop tier-A cases (`managed.rs` Rig) ran the tile jobs with `max_in_flight: 64` and a spawner that finished 24 (or 10,000) jobs per frame, so neither a worker cap nor a job duration existed; `dive.rs` used `max_in_flight: 16` and `run(6)` a frame, a fixed completion count. The 1,217 tiles/s of ADR 0032 appeared as a number in the text only. A dispatch regression (a cap, a refill that waits for the frame) was invisible: the fakes finished every dispatched job before the next frame by construction.
Assumption it changes: ADR 0032's "generation-rate model at 1,217 tiles/s" was read as the rate the streamer reaches; it is the rate the source sustains on 20 free threads. The streamer reaches it only if the number of jobs it hands out per frame covers (rate x T) and the pool has the threads.
Fix chosen: the pool size is one parameter (`GenWorkers`, default = the machine's hardware threads, `--gen-workers N` to pin it), `max_in_flight` is derived from it, and the scheduler queues `queue_ahead` more jobs behind the running ones (default = the worker count) so that a worker which finishes between two frames takes the next job from the pool's queue at once (the pool runs jobs in submission order). A completion-triggered refill from the worker side was rejected: the streamer is single-threaded and frame-driven (CON-04, CON-14), so a worker choosing the next request would need the queue under a lock and would make the request order depend on thread timing. The queued-ahead jobs are cancelled like any (the job checks its token at its start), take slots at dispatch, and commit the choice of the next N tiles up to about one job duration earlier than before.
Ad hoc after the fix (indicative only: software adapter, release, `perf stream dive --smoke` over the in-memory 256-cell bake with the smoke length raised to the 1,800 descent frames for this run, 1280x720; frames of 100-500 ms, not 16.7 ms, so jobs are far shorter than frames and the limit, not the rhythm, binds here; the RTX numbers are window 3's): old (`--gen-workers 8 --gen-ahead 0`) dispatches exactly 8 a frame from frame 300 on, in flight 8, queue up to 2,986; new (20 workers, 20 ahead) dispatches 10.1-10.6 a frame (demand-bound), queue at most 28, mean lag per altitude band 0.00 below 2,000 km against old 0.03 / 0.02 / 0.07 / 0.39 / 0.28 / 0.17 (2,000-200 km ... 20-1 m). Frame columns (median scheduler / upload / record ms) do not rise with 20 generating threads next to the frame thread: 2,000-200 km 0.17 / 0.82 / 5.14 against 0.22 / 0.78 / 5.04; 200-20 m 0.39 / 1.81 / 21.5 against 0.46 / 1.44 / 18.9 (a few more tiles uploaded and drawn); wall medians within 10%. Contention on the 20-core RTX machine at 16.7 ms frames is for window 3 and F8.

## 2026-10-16 Upload time varies with the wants and the load, not with the bytes or the queue: the ranking sets built on the frame thread (upload-time-variance, M4 fix F8, REND-018, STRM-020, TEST-012)
What happened: perf window 2 had 712 dive frames over 2 ms in `upload_ms` (median 2.69) at the median 53 KB in 2 calls that other frames write in 0.59 ms, in the low bands where tiles are generated. Ablation before any fix (software adapter, release, `test-render --perf-smoke --scene dive --allow-memory-bake --global-res 256`, smoke length raised to the 1,800 descent frames through a temporary env switch, 1280x720, frames of 100-500 ms; a temporary patch put CPU timers around each step of the managed loop's upload half and of the renderer's staging and queue calls and wrote them per frame; reverted. Not Rasierklinge's RTX run: the software adapter's rasteriser threads share the 20 cores too, which makes the contention here a bit worse, not better). The column is not the writes: `upload_ms` is `take_changes`, the class sets of the ranking, the prefetch closure, the sort, the batch and the sink call. In frames with a tile waiting, `Classes::of` (every draw tile with ALL its ancestors, no early stop, plus the closure of R, 11k tiles at the ground) ran whenever the draw or residency wants changed; the dive's camera moves, so that is nearly every frame.

|---|---|---|---|---|
| 20 | 0.55 / 12.26 / 16.23 | 88 | 0.315 / 8.46 | 0.139 / 1.11 |
| 18 | 0.56 / 8.17 / 19.03 | 65 | 0.324 / 7.93 | 0.141 / 0.44 |
| 16 | 0.58 / 6.85 / 13.95 | 59 | 0.327 / 6.73 | 0.144 / 0.41 |

In the ground band (frames 1200+, class sets rebuilt in most frames) the class sets cost a median 1.0 ms with 8, 16 and 18 workers and the p99 grows from 2.0 ms (8 workers) to 8.1 (16) and 10.4 (18): one step of about 1 ms that allocates a megabyte of hash table per frame is exposed to being descheduled or to page-fault and heap costs when 16-20 threads run beside it. Of the slow frames (over 2 ms, run with 20 workers) the class sets are the largest part: median 2.7 ms, mean 4.9 of a mean 7.6. The renderer's part is small and flat: conversion 0.026 ms, packing 0.035, `write_texture` 0.068, `write_buffer` 0.011 (medians), `upload_batch` p99 0.4-1.1 ms. The prefetch closure (rebuilt from scratch in every uploading frame) is 0.004 ms median but 12 ms at its worst once. Remaining single steps of 3-17 ms in any step (pack, `write_texture`, class sets, `take_changes`) with no relation to the work in the step are the signature of the thread losing its core.
Micro-benchmark `crates/render/examples/upload_contention.rs` (the real `upload_tiles_at` path, 6 compact tiles = 53 KB in 2 calls per frame, a frame submit, 16 ms pacing, N threads building compact tiles beside it; ms median / p99 / max): software adapter N = 0 / 4 / 8 / 16 / 20: 0.107/0.158/0.721, 0.063/0.200/0.287, 0.118/0.200/0.307, 0.126/0.189/0.207, 0.097/0.162/0.714; RTX (Vulkan) 0.321/0.363/0.435, 0.291/0.344/0.392, 0.321/0.381/0.484, 0.336/0.412/0.540, 0.318/0.399/0.751. A heap allocation of the staging size costs 0.001-0.007 ms median in the same conditions. So: not the bytes, not the queue (on RTX/Vulkan 0.27-0.29 ms of the 0.32 is the two queue calls and does not move with N), not the allocator contention of the staging (a micro effect), and the frame thread is not starved when it wakes for 0.1 ms bursts every 16 ms; it is when it runs a 1 ms step that allocates and a 6 ms record step.
Cause (software evidence): the O(|wants|) class-set build on the frame thread, each frame the draw wants change, inside the upload column; its tail is the contention with 16-20 busy threads (the tail disappears with 8 workers). Not verified on the RTX: window 3 reads `upload_ms` p99 with the full pool and the count of frames over 2 ms.
Fix (ad hoc after, same smoke, 18 workers the new default / 20): the draw class is built with walks that stop at an ancestor already at or below the priority (identical sets), in the map the last build left (kept capacity), not rebuilt unless the draw wants changed; R's class is a lookup in R (closed under parents), no set; the prefetch closure is rebuilt only when the prefetch wants change; the draw wants vector, the waiting list and the batch are kept between frames; the renderer's staging (converted texels, write lists, sort orders, run rectangle, record run, vertex bytes) lives in kept buffers; the default pool is the hardware threads less 2 (`GEN_RESERVE`). Result: upload med / p99 / max 0.23 / 0.96 / 15.4 ms and 14 frames over 2 ms with 20 workers (before 0.55 / 12.26 / 16.23, 88); 0.19 / 0.83 / 17.0 and 13 frames with 18 (the default); class sets median 0.025 ms, p99 0.14. All 13 remaining slow frames (18 workers) are one step each (staging pack or `write_texture` in 8, one class build in 4, `take_changes` in 1) of 3-17 ms with no work behind them, 9 of them in the ground band where the software rasteriser's threads and 18 generators run: that residue is the OS taking the core, which the reserve of 2 only makes less likely on a machine with a GPU instead of 20 rasteriser threads. Whether reserving cores cuts that residue cannot be seen here: the 8 / 16 / 18 / 20 table above has the tail growing from 2 ms to 8-12 ms between 8 and 16 workers, and the default of 18 is a guess between them.
Thread priority: lowering the generation threads' priority needs `SetThreadPriority` (unsafe FFI, which the project avoids; ADR 0019 "no unsafe") or the `windows-threading` crate, which is in the lock file only as a transitive dependency; not taken. If window 3 still shows a tail with the reserve, that is the next step and an ADR question.
Assumption it changes: REND-018 (the upload cost was the queue calls and the conversion: those were fixed by F5 and are 0.03-0.3 ms; the time left in the column was ranking work), STRM-020 (a worker per hardware thread is not free for the frame thread), ADR 0033 point 9 (the 2 ms upload target is met by the writes at the 1 MiB cap; the column's variance was the loop's own ranking), TEST-012 (a baseline is only comparable at the same generation pool).
Proposed follow-up: window 3 checks `upload_ms` p99 with the full pool (target 2 ms) and `upload_calls`, and, if over, which step (the log has only the column: re-run with `upload_times()` and a per-step timer); logs now record `protocol.gen` so a baseline taken with another pool is reported, not compared. The class build is still O(|D|) per delivered plan on the frame thread; moving it to the plan worker (the plan already has D) is the next step if the column's median at 2560x1440 is over 0.2 ms.
