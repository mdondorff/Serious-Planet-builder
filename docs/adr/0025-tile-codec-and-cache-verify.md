# 0025 Tile payload codec, node set id and what cache-verify finds
Status: accepted (owner's delegation of 2026-10-12: the architect accepts ADRs that reviewers find sound and unambiguous; accepted by opus-planner after the spec-guardian and numerics reviews and their text fixes)
Date: 2026-10-12
Source: m3-cache-verify (STRM-004, STRM-009, #68); written by sonnet-coder into the body of ADR 0024 after 0024 was accepted, moved here by opus-planner because accepted ADRs are not edited (CON-23); ADR 0006, ADR 0018, ADR 0019, ADR 0023, ADR 0024; constitution CON-05, CON-11, CON-14, CON-23

## Context
`cargo xtask cache-verify` and `generate --cache-dir/--verify-cache` (#68) store height tiles in the pack of ADR 0019 and check them against regeneration. Building them fixed a payload format, the node set id that ADR 0019 introduces for compaction, and the meaning of a verify result. ADR 0019 says `cache-verify` "regenerates a sample from the definition and compares bytes"; the pack bytes are not deterministic (ADR 0019, concurrency), so what is compared needs stating.

## Decision
1. **Height tile payload** (STRM-009; record kind byte 1): `codec version (u8 = 1) | cells per edge res (u32 LE; a power of two from 1 to 4096; res + 1 samples per edge) | raw length (u32 LE; must equal 4 (res + 1)^2) | LZ4 block` (a raw LZ4 block: no frame, no size prefix). The raw bytes are the `(res + 1)^2` heights, row-major (index `l (res + 1) + k`, `k` fastest), as little-endian `f32`, shuffled by byte index (all first bytes, then all second bytes, and so on). The decoder refuses an invalid `res`, a raw length other than `4 (res + 1)^2` and a block that does not decode to exactly that length, and never allocates more than that; the encoder refuses an invalid `res` and a number of heights that does not match it.
2. **What is compared.** Regeneration is the field's `f64` height at each sample's 3D unit direction, rounded to `f32` with Rust's `as` (round to nearest even), the same path that produced the stored tile. Stored and regenerated heights are compared bit for bit (`to_bits`), not as compressed bytes. This holds signed zeros apart; NaN bit patterns are not promised to be stable across platforms, which only matters for a NaN height, itself a bug. Heights relative to the radius in `f32` are what the GPU already receives (CON-11).
3. **Node set id** (the record field ADR 0019 introduces for compaction): the first 16 bytes of BLAKE3 `derive_key("planet-builder node set v1")` over the paths of the field's field-wide reads and of the body's radius node (`body.0.radius_m`, a body parameter that is not in the read set), deduplicated, sorted by UTF-8 byte order and concatenated, each as its byte length (u32 LE) followed by its UTF-8 bytes, with no count prefix. It is per *world*: a field that reads cells gets per-tile query paths in its keys but not in this id. That is conservative (no live record can look dead), but dead cell-reading tiles then look live and are reclaimed only by LRU eviction; it should become per tile before cell-reading fields are stored, and compaction may then evaluate the cell query from the current definition (no regeneration). The id is defined for the height kind; a mesh kind defines its own when meshes are stored.
4. **What `cache-verify` finds.** Every entry is decoded first, so a damaged entry, stale or not, is *unreadable* and fails the run. The definition's key is computed at the resolution the payload claims. An entry is *stale* when its key is no longer the definition's key: *explained* when its generator version, hash version or node set id differ from the current ones, *without a known reason* when they are all equal (a node value changed, which ADR 0019 calls reclaimable only by LRU, or the key function drifted, which the pinned known answers of STRM-003 catch). Stale is not an error. An entry under the current key must carry the current metadata and equal its regeneration; a record that does not was written wrongly or has an input missing from its key. **A run that compared nothing fails**, unless the caller passes `--allow-stale` and at least one entry is stale; `--allow-stale` covers stale entries of both kinds. Regenerating from the same definition and generator finds nondeterminism, damage and wrongly written records; it finds an input missing from a key only when that input's value differs between building and verifying.
5. **Scope today.** Only body 0 is stored and verified; meshes are not verified. A record whose hash version differs from its store's is reported only when it sits under the current key; otherwise it counts as explained stale. Not built yet: compaction, the size cap and LRU eviction, paging the index in blocks, an in-process writer thread, logging, the streamer using the store (through an injected interface, CON-04). No `fsync` is done: every index is checked against the data and rebuilt when stale, and every payload against its CRC.

## Amends ADR 0019 (in part, CON-23), and updates ADR 0024 point 11
- `cache-verify` compares decoded `f32` bits (point 2), not bytes.
- The node set id (point 3) is a domain-separated `derive_key` with length-prefixed, deduplicated paths, adds the radius node, which is not in the read set, and covers only field-wide reads, so it is per world, where ADR 0019 says "BLAKE3-128 of the sorted paths of the read set".
- ADR 0024 point 11's "not built yet" list is out of date for compression, `cache-verify` and `generate` using the store; point 5 here is the current list. ADR 0024 itself is not edited.

## Consequences
- A second implementation can decode and verify stored height tiles from ADR 0019, 0024 and this ADR.
- Code follow-ups: an empty run (nothing compared and nothing stale: an empty store, all packs skipped, only unsupported kinds) still passes with 0 checked; it must fail as point 4 says, with a test. The node set id needs a requirement and a pinned known answer, like the keys (ADR 0023 point 9).
