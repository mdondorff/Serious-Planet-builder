# 0034 GPU clock state in performance measurements
Status: accepted with a change (owner, 2026-10-15, opus-planner session): GPU figures (`gpu_ms`, the GPU budget, cross-session GPU comparisons) need P0 as proposed; the frame-time verdicts (median and p99 of `frame_ms`, CON-21) stay valid at whatever clock state the driver chose, because that is what a user sees, and print the clock state next to them (point 4 amended below). The code of #131 marks `frame_ms` NOT VALID outside P0 and is changed to match (queue item 6d).
Date: 2026-10-15
Source: `docs/learnings.md` 2026-10-15 (ground-1m GPU median 2.9-3.0 ms at P0, about 1.4 GHz, on 2026-10-11; 4.1-4.2 ms at P2/P3, about 1.15 GHz, on 2026-10-13); SPIKE-06 (`docs/spikes.md`: the same code read 2.85-6.0 ms between process runs); `docs/status.md` M4 item 6b; ADR 0020; TEST-012; constitution CON-20, CON-21

## Context
ADR 0020 makes a perf session valid when the machine was ready before the run, no throttling was seen and the run-to-run noise was at most 10 %. It does not look at the GPU's clock state. The ground-1m frame is CPU-bound (plan 6.6 ms, encode 6.0 ms, GPU 3-4 ms), so the GPU is idle about half of each frame and the driver may leave it in a low performance state: the same code measured 2.9-3.0 ms at P0 and 4.1-4.2 ms at P2/P3, and SPIKE-06 saw 2.85-6.0 ms between process runs. Within one session the noise rule does not see this (a whole session sits in one state), and across sessions the regression report (TEST-012) compares GPU medians as if the clock were a constant: the apparent rise of 2026-10-11 to 2026-10-13 may be clock state, not the 44-byte vertex. The harness already records `nvidia-smi` clocks.gr, clocks.mem, pstate and the throttle reasons before and after every run (`ClockSample`, `clocks_before` and `clocks_after` in the log), but the only thing acting on the P-state is a session warning (`session_warnings`) when a run starts at P5 or lower, which makes the whole session not valid. No constitution rule changes: CON-21 asks for a measured, reproducible machine state and this makes the GPU part of it.

## Options (with trade-offs)
1. Status quo: record the state, judge nothing. Cheap, and the GPU budget verdicts and regression reports stay unreliable.
2. Invalidate the whole session when a view is outside P0. Simple, but CPU plan and record times are unaffected by the GPU clock and would be thrown away with it.
3. **Warm up to the loaded state, mark a view measured outside P0 not valid for GPU figures, compare GPU figures only at equal clock state** (chosen). CPU figures keep their value; the architect sees the state next to every GPU number.
4. Pin the clocks with `nvidia-smi --lock-gpu-clocks`. Needs administrator rights and changes the machine's state under a fixed profile that CON-21 asks to be the performance profile; rejected.
5. Make the workload heavier so the GPU stays busy (for example a supersampled target). Changes what is measured; rejected.

## Decision
Option 3, an amendment in part of ADR 0020 (its readiness gate, the validity rules after the run and the owner's rights are unchanged; this ADR adds a clock-state rule to the measurement and to the regression report).
1. **How the state is read.** As the harness does today: one `nvidia-smi --query-gpu` call (`NVIDIA_SMI_ARGS`) giving `pstate` and `clocks.gr`; a missing or unparseable reading is "unknown" and never a pass. No other tool is used (a driver API would add a dependency for the same numbers).
2. **Clock state of a view** (the granularity of every rule below is the view, not the run) = the P-state and the median graphics clock of all samples taken before and after the runs of the view's final batch (a noise retry discards the first batch; the log's `clocks_before` and `clocks_after`). If the samples disagree on the P-state (one P2 sample among them is enough) or one is missing, the view has no clock state and the reason says so ("mixed P0/P2", "no sample"). The first run's before-sample is read right after the last warm-up chunk, so it shows the loaded state.
3. **Warm-up to the loaded state.** After the plan is made and before a view's runs, the harness renders the view in chunks of 60 frames and reads the state after every chunk until it reads P0, up to a **cap of 30 s per view**. The cap is a measured limit and not a constant to tune: the time it took (or that the cap was hit) and the last reading are recorded in the log (`warmups`) and printed. The existing fixed warm-up frames still run first; the heaviest view runs first, so later views usually find P0 already. When the cap is hit the harness does not refuse: the session goes on and the view is marked by point 4 (the CPU figures are still wanted). The loop is a function in `planet_perf` taking the render, the sampler and a clock as closures (so tier A drives it with fakes and a fake time source); the cap is inclusive (a reading of P0 at exactly the cap counts). The readiness gate itself is unchanged. **Open (the first window measures it):** a light view by design (orbit) may never reach P0, and SPIKE-06 saw sustained clocks near 1.05 GHz after a 4 s warm-up, so P0 may be unreachable for some views; those views simply have no GPU verdict and cost the cap once each. If the first window shows that P0 is the wrong criterion, the architect proposes a recorded clock band instead.
4. **A view whose clock state is not P0 is NOT VALID for GPU figures.** A view is GPU-valid only if its clock state exists and is P0. Assumed, not shown (the first window checks it against the clock states): `cpu_ms` (record time) does not wait for the GPU. Not valid: the GPU time (`gpu_ms`) and the frame wall time (`frame_ms`, which includes waiting for the GPU) of that view, and with them the GPU budget (median 8 ms) and the p99 frame verdict. Still valid: `cpu_ms`, `plan_ms` and every count. The session's `valid_for_budgets` (throttling, noise, power scheme, adapter) is not changed by this; each run of a view carries the view's `gpu_valid` (and `gpu_invalid_reason`) in the log. The existing session-level rule stays: a run that starts at P5 or lower (`session_warnings`) still makes the whole session not valid; the new rule is the finer one for P1 to P4 and for mixed states. The console prints `NOT VALID for GPU budgets (P2, 1150 MHz)` in place of the `ok`/`OVER` of the GPU and frame verdicts of that view, with the measured medians still shown, and the session summary line lists the views affected.
   **Amended by the owner, 2026-10-15:** `frame_ms` and its median and p99 verdicts are not withdrawn outside P0: they are judged as measured, with the view's clock state (or its reason) printed next to them and recorded in the log; only `gpu_ms`, the GPU budget and cross-session GPU comparisons follow the P0 rule. Frame-time medians are compared across sessions as CPU figures are, with the clock states of both sessions printed beside the comparison.
5. **Equal clock state** = the same P-state and graphics clocks within **5 %** of the larger (1.40 GHz and 1.35 GHz are equal; 1.40 and 1.15 GHz, 18 %, are not). Only P0 can be GPU-valid (point 4), so in practice this compares P0 against P0; a P0 session at a different boost clock beyond the tolerance is "not comparable" too.
6. **The regression report compares `gpu_ms` and `frame_ms` medians only between GPU-valid views at equal clock state.** `cpu_ms`, `plan_ms` and the counts are compared as before. When the view of the new session is not GPU-valid the report says `GPU medians of <path> not compared: NOT VALID for GPU budgets (<state>)`; when the baseline's differs it says `not comparable: clock state <old> vs <new>` (old and new as `P0 1395 MHz`). A log written before this ADR is read through the same rule from its recorded samples.
7. **Baselines.** The existing `terrain.last-valid.json` stays the baseline for the CPU figures and the counts. A second file `terrain.last-gpu-valid.json` keeps the last valid session in which at least one view was GPU-valid and is the baseline for the GPU figures, compared per view (a view that was not GPU-valid in it has no GPU baseline: `not compared`), so a session at P2 does not displace the P0 baseline and one flaky light view does not block the others; the cost is that a session with a single valid view replaces the GPU baseline of the other views. Before the file exists the previous log stands in, as for the first baseline. The field, frame-size and invalid-session rules of TEST-012 apply to both files. Only a valid session writes either file.
8. **What the architect sees.** Next to each view's verdict: `P0 1395 MHz` (the clock state) or `NOT VALID for GPU budgets (<state or reason>)`; per view one warm-up line (`warm-up ground-1m: P0 after 3.2 s (4 chunks)` or `warm-up ground-1m: still P2 1150 MHz after 30.0 s cap`); in the comparison lines the `not comparable: clock state ...` or `not compared` lines above. The log carries the same facts.

## Consequences
- The GPU budget verdict becomes meaningful again; the question whether #65's vertex format raised the GPU time (ADR 0033 context) can be answered by a P0-to-P0 comparison. The 2026-10-13 figures (P2/P3) are not GPU-valid under this rule and are not retroactively changed.
- A view that never reaches P0 inside 30 s gives no GPU verdict; the architect then retries in another window or asks for a heavier warm-up. Cost: up to 30 s per such view.
- The `nvidia-smi` calls (about 50 ms each) happen between chunks, outside measured frames.
- Tests (tier A, no GPU): the clock state of a view, the P0 rule, the equal-state rule with the tolerance, the warm-up loop with a fake sampler and renderer (reaches P0, hits the cap, an unreadable sampler), the report with recorded fixtures (valid vs valid, P0 vs P2 not comparable, new view not P0, old log without the new fields, CPU figures compared regardless), the log's `gpu_valid`. The platform query itself stays thin and is not run in tier A.
- Not run on the reference GPU by the author of this change; the first perf window by the architect exercises it.
- TEST-012 gains a requirement text and scenarios for points 3 to 7 (scenarios under TEST-012, tier A tests citing it as the existing gate tests do; `Verify: C` stays for the workload itself), and `budget_verdict` gains a third state (not valid); ADR 0020's text is untouched.
