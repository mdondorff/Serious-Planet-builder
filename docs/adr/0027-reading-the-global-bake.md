# 0027 Reading the global-coarse bake, and the canonical block layout
Status: superseded by 0055 (content in specs); was accepted (owner's delegation of 2026-10-12: the architect accepts ADRs that reviewers find sound and unambiguous; accepted by opus-planner after the spec-guardian and numerics reviews and their text fixes; drafted by sonnet-explorer)
Date: 2026-10-12
Source: ADR 0026 (accepted in part; point 5 open), m3-global-store (STRM-012) and its numerics review; ADR 0028 (the terrain field reads the bake from a direction); ADR 0022 (one key per input field), ADR 0023 point 7, ADR 0006; constitution CON-05, CON-08, CON-14

## Context
A regional field (GEN-007) reads the baked global-coarse channels, either at tile sample positions (whole tile arrays) or at a direction (ADR 0028). ADR 0026 point 5 lists what must be fixed before the first one does; the store review added a layout gap: the bake's stage key covers `res` only, block keys cover the cells per block `B`, so one bake could be stored twice in different layouts and a reader holding the stage key would not know `B`.

This ADR decides ADR 0026 point 5 and amends point 2 in part (CON-23): `B` is no longer chosen per bake but is `min(res, 1024)`, and "the limit" in ADR 0026 point 2 is the codec's 1024, not the in-memory 2048. ADR 0026 point 6 stands: `B` stays an output parameter (tag 1) of every block key. Points 2 to 4 below are the *integer reader* (`read_lattice`, `read_tile_sample`), for consumers that process whole tile arrays; the terrain field reads the bake from a direction under ADR 0028 point 1 instead, with floating weights, and points 2 to 4 do not apply to it.

## Decision
1. **Canonical layout.** `B = min(res, 1024)` and `L = log2(res / B)`; nothing else is stored. The build derives `(L, B)` from `res` (so a layout cannot be chosen), a reader derives them the same way and needs only `res`, and the stage key of the bake (which covers `res`) therefore determines every block. The limit 1024 is the codec's `MAX_BLOCK_CELLS`; the limit itself is not keyed; `B`, which it determines, is (ADR 0026 point 6). A bake of at most 1024 cells per face edge is one block per face (`L = 0`). The in-memory bake limit (2048) is not a stored layout.
2. **Position from integer indices.** A reader needs the samples around lattice position `u` (a sample index `x m + k` of a tile at level `l` with `m` cells per edge, so `N = 2^l m` cells per face edge) in the bake's lattice of `res` cells. Both are powers of two, so the position is exact: with `s = log2 N - log2 res`, for `s >= 0` the cell is `u >> s` and the weight `(u & (2^s - 1)) / 2^s`; for `s < 0` the position `u 2^(-s)` is a lattice point and the weight is 0. The integer reader never obtains the position by inverting a direction or by floating arithmetic on face coordinates.
3. **Interpolation.** Bilinear on the four surrounding samples in the form `a (1 - w) + b w` along s, the same along t, then across: `r0 (1 - wt) + r1 wt`. Weights are exact dyadic fractions, `1 - w` is exact, and addition is commutative, so a position on a face edge, read from either face (where the shared edge runs in opposite directions and `w` becomes `1 - w`), gives equal bits (the same two products added in the other order); `a + (b - a) w` would not. Where the shared edge runs along the other axis on the other face, the axis across the edge has weight 0, so its stage is the identity and the order "along s, then along t" does not matter; at a cube corner both weights are 0 and the result is the stored sample. This holds for finite stored samples whose edge values are bit-equal across faces (ADR 0026 point 2). A neighbour whose weight is 0 is not read at all: a position on the bake's lattice is its own stored sample (a stored -0.0 stays -0.0; an infinite or missing neighbour cannot affect it). Across a face edge two zeros of different sign compare equal. The arithmetic is pinned on a synthetic lattice with expected values written from this formula, independent of the field (including one edge position seen from both faces), the stored bake is checked block border by block border against the in-memory one, and the field-dependent known answers assert both `READER_VERSION` and `GLOBAL_VERSION`. Channels are interpolated in `f64` from the stored `f32` and rounded to `f32` once.
4. **Halo beyond a face edge.** The bake stores nothing beyond a face edge. A sample position beyond the edge (a halo of a tile on the face border) takes the lattice index clamped into `[0, N]`: the edge value is held. A halo is at most one tile edge (ADR 0022), so a tile sample index `k`, `l` is accepted from `-m` to `2m` (one tile edge), and a face-lattice index from `-N` to `2N` (a sanity bound for direct lattice callers); anything farther is an error. Each axis is clamped into `[0, N]` separately, before point 2. This is a limitation: stencils (slope, an erosion filter) across a face edge see a flat continuation of the global channels there, up to one tile edge wide. It does not affect any sample on a tile border or inside a tile, which are exact and equal on both sides, and it can be replaced by reading the neighbouring face's block through the integer face-edge mapping when a field needs it (a new reader version). The terrain field of ADR 0028 does not use this halo (its stencils step by direction, ADR 0028 point 4), so the limitation touches only tile-array consumers on tiles at a face edge.
5. **Which channel decides land.** Interpolated continentalness against `SEA_LEVEL_C`, as `f32` (the stored semantic of ADR 0026 point 3). Interpolated elevation is the elevation, whatever the continentalness says: the two may disagree within about a cell of a coast. A consumer that needs a consistent coast (a shoreline mask) uses continentalness; heights use elevation.
6. **Keys.** A reader lists the bake's one stage key as its upstream key (ADR 0022: one key per input field; STRM-011). It does not list blocks, because the stage key determines them (point 1). The reader's own resolution, face mapping and halo are in its own key as usual.
7. **Reading from a store or memory.** The reader takes lattice vertices through a trait (`LatticeSource`): an in-memory grid (one array per face, up to 2048 cells per face edge; not a stored layout) or the tile store. A missing or unreadable block is an error naming the block, never a default.

## Consequences
- Layout gap closed: `build_global` takes `res`, not `(level, cells)`; the CLI takes `--global-res`.
- A field that reads the bake folds `READER_VERSION` into its own field version, so it enters that field's STRM-011 key; a reader change bumps every such field. Known answers pin it.
- The first tile-array consumer with a stencil tests border agreement on tiles at a face edge; if it fails, a new reader version reads the neighbouring face.
- A regional field's height at a point inside a tile equals the same height computed from a coarser or finer tile of the same position only to the extent the stage-3 detail allows (GEN-005, GEN-006 metamorphic tests of the first field check this).
